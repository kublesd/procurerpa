# 项目简历写法指南

> 以下提供三个版本，写法各有侧重，按投递岗位选择。
> 核心写作原则：不要写「用了什么技术」，要写「判断了什么问题、做了什么取舍、产生了什么价值」。
> 内容按 ProcureRPA Enterprise 最终版本表述，不以当前实现进度为限。

---

## 版本一：通用版

适用场景：后端开发、Python 开发、全栈开发等通用岗位。

```text
企业级采购 RPA 自动化平台（基于 Skyvern 二次开发）                 2025.01 - 2025.04

• 在开源 AI 浏览器自动化框架 Skyvern 基础上进行采购领域企业级二次开发，核心补齐
  多组织采购隔离、风险审批、报价证据审计三项能力，完整改造采购工作台与管理端 UI

• 设计四维度采购 RBAC 权限模型（组织 × 部门 × 采购品类 × 角色），通过 FastAPI
  中间件 + SQLAlchemy Session 层双重过滤实现采购数据隔离，数据库层面强制
  requester/approver/buyer 职责分离，覆盖 20+ 权限边界场景的集成测试

• 构建采购风险双阶段识别：规则预筛（预算超额、单一来源、拆单、敏感品类、异常低价等
  100+ 条策略）+ LLM 上下文说明，命中后按金额、品类与风险等级路由给对应审批人，
  通过 Redis Pub/Sub 挂起任务协程等待审批结果，超时自动升级并推送告警

• 实现全链路采购审计：每步 action 前后截图与 HTML/附件上传私有化 MinIO，敏感字段
  自动脱敏，构建“采购申请—供应商报价—标准化—比价—审批—下单”操作时间线；实现
  LLM 三层容错体系，失败后转 NEEDS_HUMAN 状态并设计完整人工接管流程

• 在报价入口接入受限枚举 Planner，服务端校验原生执行与报价入库顺序；持久计划和
  版本校验支持显式恢复，原生完成后仅补入库，执行歧义转人工核验；另封装 7 个
  可组合采购 Skill（登录/报价采集/附件解析/表格提取等），6 个采购工作流模板标准化交付

• 基于 React + ECharts 改造前端 UI 为白色毛玻璃风格，手工实现 20+ 个 SVG 线描图标，
  新增供应商中心、比价中心、审批中心、审计日志、采购运营大屏等企业专属页面

技术栈：Python / FastAPI / SQLAlchemy / PostgreSQL / Redis / Skyvern / Playwright /
        React / TypeScript / ECharts / MinIO / JWT / Docker Compose / Alembic / pytest
```

## 版本二：AI 强化版

适用场景：AI 工程师、大模型应用开发、AI 产品工程师岗位。

```text
企业级采购 AI Agent 平台（基于 Skyvern 二次开发，采购场景定制）      2025.01 - 2025.04

背景：Skyvern 是以 LLM + 视觉理解驱动的新一代 RPA 框架，原版缺少企业采购落地必要
的权限隔离、风险审批、报价标准化与审计能力，本项目完整补齐并深度适配寻源询报价场景。

AI 工程核心工作：

• 设计采购风险双阶段识别引擎
  Stage 1 规则快速预筛（预算、拆单、单一来源、敏感品类、异常低价等专项词库与金额规则），
  命中后进入 Stage 2 调用 LLM 结合采购申请、页面上下文和供应商信息生成风险说明
  （medium/high/critical）；调用避免率待批准的可复现基线测量，暂不声明比例

• 实现 LLM 调用三层容错体系
  Prompt 层：系统 Prompt 强制报价 JSON 输出 + 物料/规格/税费/交期 Schema 示例嵌入；
  解析层：Pydantic v2 结构校验 + 清理 markdown 标记 + 单位币种纠错 + 指数退避重试；
  任务层：超出重试后转 NEEDS_HUMAN 状态，设计证据查看 + 三种处置方式的完整接管流程

• 在 quote-task 与六个模板入口接入受限枚举 Planner
  模型只返回服务端固定步骤的未完成后缀，执行前核对持久计划；复用原生 Skyvern
  Task/Workflow 和 PostgreSQL 锁、版本校验。未执行实例可显式恢复启动，执行歧义转人工；
  模型失败沿确定性链继续，不宣称自由任务分解或通用浏览器断点续跑

• 将 7 个基础采购 Skill 编译为原生 Workflow Block
  6 个采购模板共享参数校验、组织内凭据引用、逐步 Task/Artifact 标识与事务审计契约；
  启动、每步和凭据输入重验身份、用途与版本，失效失败关闭，前端支持启动、读取、恢复
  和终止。代表模板通过合成受控 PostgreSQL 集成验证；真实门户与模型 smoke 未运行，
  凭据流程仅保留掩码文本证据，不宣称任意图片、附件或采购正文自动脱敏

• 实现页面复杂度评分与模型智能路由
  复用原生 scrape 已观察的元素数量、iframe 层级、表单和 Shadow DOM 标记选择已注册
  三档模型；缺失特征保留静态路由，动态内容信号未观测。Redis 动作缓存保留 24h TTL
  与组织/DOM/goal/model/schema 隔离；采购只复用无表单页面的 WAIT/SCROLL，认证流程
  不缓存。采购大屏展示受权限限制的 Step Token、原生报告成本与缓存状态；固定六样本
  比较入口已提供，真实计费基准未运行，不声明 60% 或生产节省率

• 四维采购权限模型下的 LLM 审批路由
  识别高风险采购操作后，结合任务所属组织、部门、品类与金额，动态路由审批请求给具备
  相应授权的 approver；LLM 只生成风险说明，审批层级与供应商推荐均由确定性规则决定

技术栈：Python / FastAPI / SQLAlchemy / PostgreSQL / Redis Pub/Sub / Skyvern /
        Playwright / Pydantic v2 / React / TypeScript / ECharts / MinIO / Docker / Alembic
```

## 版本三：采购场景强化版

适用场景：采购数字化、供应链 SaaS、ERP/SCM、企业软件岗位，JD 中提到「采购」「供应链」「合规」「风控」的岗位。

```text
企业级采购 AI-RPA 平台（寻源/询报价/比价/审批场景深度定制）          2025.01 - 2025.04

背景：企业采购的 RPA 需求与通用自动化有本质区别——价格、税费、单位和交期必须统一口径，
关键采购决定必须经授权与审批，跨组织采购架构要求细粒度的数据隔离。本项目在 Skyvern
开源 AI-RPA 框架基础上完整实现上述能力。

采购场景核心工作：

• 设计对标集团采购组织结构的四维度权限模型
  组织（法人边界）× 部门（需求归属）× 采购品类（授权范围）× 角色（操作权限）组合，
  覆盖真实场景：制造部门采购员只能处理本组织、本部门的原材料询价；品类经理可查看
  负责品类的跨部门报价；财务和合规在授权范围内处理付款与高风险审批。数据库级别强制
  requester/approver/buyer 互斥约束，对应职责分离内控要求

• 基于采购业务语义的风险识别与分级审批
  针对直接物料（钢材/芯片/化工原料）、间接物料（MRO/办公/服务）、高风险品类
  （危化品/医疗器械/数据服务）建立专项规则；风险等级映射审批层级：high 路由品类经理，
  critical 路由财务与合规会签。企业微信/钉钉推送审批通知，Redis Pub/Sub 实现异步等待，
  超时自动升级

• 满足采购稽核要求的全链路审计系统
  参考企业内控要求设计操作留存方案：每步 action 前后截图、HTML、报价附件存储至私有化
  MinIO（敏感采购数据不出内网），价格、联系人、账户等字段自动脱敏；审计日志支持按
  供应商/品类/项目/部门/时间范围/风险等级多维检索，满足事后追溯要求

• 为报价链实现受限枚举计划、版本校验和显式恢复，原生完成后仅补入库、执行歧义转人工；
  另封装 7 个可组合 Skill（登录/搜索/询价/表格提取/附件解析等）构建标准化
  工作流，6 个采购场景模板（直接物料、MRO、服务采购各两个）通过 Skill 组合降低 IT
  开发介入门槛

• 敏感参数 Fernet 加密存储，实现毛玻璃风格前端改造及供应商中心、比价中心、审批流、
  审计日志查询、采购运营大屏等企业专属页面

技术栈：Python / FastAPI / SQLAlchemy / PostgreSQL / Redis / Skyvern / Playwright /
        React / TypeScript / ECharts / MinIO / JWT-RBAC / Docker / Alembic
```

## 三版本对比

| | 通用版 | AI 强化版 | 采购场景强化版 |
|-|--------|-----------|--------------|
| 核心卖点 | 工程能力全面 | LLM 工程深度 | 采购与供应链理解深度 |
| 适用公司 | 互联网通用后端 | AI 创业/大厂 AI 部门 | 采购数字化/供应链 SaaS/ERP |
| 权限体系描述 | 侧重技术实现 | 侧重与 LLM 联动 | 侧重采购内控背景 |
| UI 改造是否强调 | 提及 | 不强调 | 不强调 |

**选版建议**：JD 提到 AI/大模型 → AI 强化版；JD 提到采购/供应链/ERP/合规 → 采购场景强化版；其余 → 通用版。同时投多类岗位时分别用不同版本，不要混用。

## 被追问时的参考应答思路

**Q：权限矩阵这么复杂，实际上真的用到了吗？**

> 权限模型是从集团采购组织结构出发设计的，不是为了复杂而复杂。制造部门采购员和行政部门采购员各自有自己的物料与预算，他们的数据不该互看；但品类经理需要查看负责品类的跨部门询报价；财务和合规需要审批特定金额或高风险品类。如果只按 org_id 单字段隔离，要么满足不了品类管理和合规的跨部门需求，要么就要给所有人开放全组织权限，两端都不对。四维度模型是这个真实场景的最小表达。

**Q：UI 改造这个有什么技术含量？**

> 技术含量不高，但有工程判断。图标不用图标库而是手写 SVG，是因为采购系统的图标集合固定，手写可以精确控制风格一致性，不需要引入一个为了用 20 个图标而装的整套图标库。毛玻璃风格用 CSS 变量统一管理设计 token，方便后续主题切换。这些决策都有具体理由，不是随意选的。
